## 1. Purpose and Scope

The policy system in Omnigent governs agent behavior by dynamically allowing, denying, or requesting human approval (`ASK`) for actions at defined enforcement points during agent execution. It enforces policies at crucial phases such as request input, tool calls, tool results, and LLM interactions. This page explains:

- Core policy classes and types
- The policy registry and function/prompt/CEL-based implementations
- Construction and operation of the policy evaluation engine
- Approval cycles and elicitation requests
- Session policy CRUD routes and how policies are enforced using hooks

Sources: [omnigent/runtime/policies/builder.py:1-162](), [omnigent/policies/types.py:1-158]()

## 2. Policy Base Classes and Types

### 2.1 Policy Verdict and Results

The core contract for policy evaluation is formalized through type definitions and result structures (`[omnigent/policies/types.py:80-158]()`):

- **PolicyAction**: Enum representing the outcome (`ALLOW`, `DENY`, or `ASK`) of policy evaluation at a given phase.
- **PolicyResult**: Dataclass containing evaluation results including `action`, `reason`, `state_updates`, and `elicitation_request`.
- **FAIL_CLOSED_PHASES**: Tuple identifying phases (`PHASE_TOOL_CALL` and `PHASE_REQUEST`) where failures to evaluate default securely to `DENY` (`[omnigent/policies/types.py:80-80]()`).

### 2.2 EvaluationContext

The evaluation context provides all required inputs for a policy evaluation call (`[omnigent/policies/types.py:84-158]()`):
- `phase`: Enforcement point enum value.
- `content`: Phase-specific payload.
- `tool_name`: Resolved tool name for tool-related phases.
- `trajectory`: Recent conversation history.
- `usage`: Cumulative token usage and cost accounting (`[omnigent/policies/schema.py:60-79]()`).
- `session_state`: Ephemeral key-value store per evaluation turn.

Sources: [omnigent/policies/types.py:80-158](), [omnigent/policies/schema.py:60-79]()

## 3. Policy Registry and Implementations

### 3.1 Function Policies

Function policies delegate evaluation to registered Python callables (`[omnigent/policies/function.py:77-112]()`).
- **FunctionPolicy** wraps a callable receiving an `event` dict and optional `config`.
- Supports asynchronous execution or synchronous offloading via `asyncio.to_thread` (`[omnigent/policies/function.py:185-187]()`).
- Supports per-turn reset delegates (`reset_turn()`) for stateful counters.
- Built-in safety policies like `max_tool_calls_per_session` and `detect_loop` are implemented as function policies [omnigent/policies/builtins/safety.py:100-162]().

### 3.2 Prompt Policies (LLM-backed)

Prompt policies utilize an LLM model and prompt templates to classify events, wrapping inputs in spotlit nonces to mitigate prompt injection.

### 3.3 Cost and Budget Enforcement Policies

Administrative cost policies gate session resource spend (`[omnigent/policies/builtins/cost.py:1-41]()`):
- **cost_budget**: A factory that creates policies to enforce cumulative LLM spend limits. It uses `ask_thresholds_usd` for soft warnings and `max_cost_usd` for hard limits, potentially forcing model downgrades [omnigent/policies/builtins/cost.py:8-28]().
- **user_daily_cost_budget** and **user_period_cost_budget**: Policies that track and enforce cost budgets on a per-user daily or periodic basis [omnigent/runtime/policies/builder.py:57-67]().
- Fails closed if pricing is unavailable to prevent unpriced execution bypass [omnigent/policies/builtins/cost.py:36-41]().

Sources: [omnigent/policies/function.py:77-187](), [omnigent/policies/builtins/cost.py:1-41](), [omnigent/policies/builtins/safety.py:100-162](), [omnigent/runtime/policies/builder.py:57-67]()

## 4. Policy Engine and Composition

The central orchestrator is `PolicyEngine` (`[omnigent/runtime/policies/engine.py:42-122]()`).

### 4.1 Construction

Built via `build_policy_engine()` (`[omnigent/runtime/policies/builder.py:1-52]()`), merging session-scoped, agent-scoped, and default policies with caching layers. This includes:
- Agent-defined policies from `AgentSpec` [omnigent/runtime/policies/builder.py:165-170]().
- Session-scoped policies stored in the database [omnigent/runtime/policies/builder.py:124-134]().
- Default policies configured at the workspace level [omnigent/runtime/policies/builder.py:109-120]().
- Unconditionally injected safety policies like `_ASK_ON_ADD_POLICY_SPEC` and `_ASK_ON_SCHEDULED_TASK_CHANGE_SPEC` [omnigent/runtime/policies/builder.py:78-103]().

### 4.2 Evaluation Lifecycle

- Iterates through policies in YAML declaration order.
- `DENY` short-circuits immediately.
- `ASK` results accumulate for human approval.
- `ALLOW` proceeds if no blocks are triggered.
- The engine manages `session_state` and `usage` updates based on policy results [omnigent/runtime/policies/engine.py:300-340]().

Sources: [omnigent/runtime/policies/builder.py:1-170](), [omnigent/runtime/policies/engine.py:42-122](), [omnigent/runtime/policies/engine.py:300-340]()

## 5. Session Policy CRUD and Hooks Enforcement

Policies scoped to sessions are persisted via policy stores and enforced via HTTP hooks registered on FastAPI routes (`[omnigent/server/routes/sessions/routes_hooks.py]()`), managing elicitation lifecycles and SSE event streams.

### 5.1 Policy Evaluation Hook

The `POST /sessions/{session_id}/policies/evaluate` endpoint (`[omnigent/server/routes/sessions/routes_hooks.py:300-300]()`) allows external systems (like native harnesses) to request policy evaluations for specific events (e.g., `PHASE_TOOL_CALL`, `PHASE_TOOL_RESULT`, `PHASE_LLM_REQUEST`).
- It constructs an `EvaluationContext` and calls `build_policy_engine` to get a fresh engine for evaluation [omnigent/server/routes/sessions/routes_hooks.py:36-37]().
- The verdict (`POLICY_ACTION_ALLOW`, `DENY`, `ASK`) is returned to the caller [omnigent/server/routes/sessions/routes_hooks.py:400-400]().

### 5.2 Permission Request Hook

The `POST /sessions/{session_id}/hooks/permission-request` endpoint (`[omnigent/server/routes/sessions/routes_hooks.py:157-157]()`) handles permission requests from native harnesses (e.g., Claude Code, Kimi, Devin).
- It receives a `PermissionRequest` payload, publishes an `elicitation_request` SSE event to the web UI, and long-polls until a verdict arrives via the session `approval` event path [omnigent/server/routes/sessions/routes_hooks.py:170-183]().
- The response format follows the native harness contract (e.g., `hookSpecificOutput.decision.behavior` as "allow" or "deny") [omnigent/server/routes/sessions/routes_hooks.py:183-185]().

### 5.3 Approval Cycles and Elicitations

When a policy returns an `ASK` verdict, an `ElicitationRequest` is generated (`[omnigent/policies/types.py:400-400]()`).
- This request is published as an SSE event to connected clients (e.g., web UI, REPL) [omnigent/server/routes/sessions/routes_hooks.py:179-180]().
- The client then sends an `approval` event back to the server via `POST /v1/sessions/{session_id}/events` to resolve the elicitation [tests/server/integration/test_sessions_permission_request_hook.py:107-118]().
- The REPL (Read-Eval-Print Loop) specifically handles `ElicitationRequest` events and waits for user input to approve or deny, then patches the verdict back to the server [tests/e2e/test_repl_approval_e2e.py:7-11]().

Sources: [omnigent/server/routes/sessions/routes_hooks.py:36-400](), [omnigent/policies/types.py:400-400](), [tests/server/integration/test_sessions_permission_request_hook.py:107-118](), [tests/e2e/test_repl_approval_e2e.py:7-11]()
