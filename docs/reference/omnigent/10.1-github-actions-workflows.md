## Workflow architecture and data flow

### Shared patterns

Several test workflows invoke `security-gate.yml` before selecting or running test jobs. The supplied definitions show the gate wired as a reusable workflow, with `contents: read` and `pull-requests: read` permissions. CI, E2E, integration, UI E2E, and UI snapshot workflows also define path filters, concurrency groups, or dependency-scope steps to avoid unnecessary work. [`.github/workflows/ci.yml:12-80`]() [`.github/workflows/e2e.yml:18-115`]() [`.github/workflows/integration.yml:11-91`]() [`.github/workflows/e2e-ui.yml:15-104`]() [`.github/workflows/ui-snapshot.yml:42-127`]()

Mock-based test workflows explicitly avoid depending on real provider credentials. E2E and integration blank provider credentials in their environments; the UI E2E workflow documents that its tests use mock values through the test server fixture. The shared `.github/actions/e2e-run/action.yml` also sets `OMNIGENT_SKIP_WEB_UI=true` and blanks provider keys before installing and running tests. [`.github/workflows/e2e.yml:58-66`]() [`.github/workflows/integration.yml:36-45`]() [`.github/workflows/e2e-ui.yml:46-64`]() [`.github/actions/e2e-run/action.yml:54-90`]()

## Security and trust model

### Deterministic security scan

`security-scan.yml` defines one PR security scan that statically analyzes the PR diff and changed-file list. Its comments specify that the scan does not execute untrusted PR code and does not use secrets on fork PRs. The scanner scripts are fetched from `main` into the workspace before the PR head is checked out separately under `pr/`; the PR therefore does not supply the scanner implementation used for its own scan. [`.github/workflows/security-scan.yml:3-17`]() [`.github/workflows/security-scan.yml:41-69`]() [`.github/workflows/security-scan.yml:96-105`]() [`.github/workflows/security-scan.yml:130-155`]()

The scan workflow obtains maintainer data, evaluates a trust gate using `should-scan.sh`, and, when scanning is enabled, fetches the PR diff and changed-file list. It then runs secret scanning, exfiltration scanning, and a sensitive-path guard. The supplied excerpt also shows a Dependabot-specific action-pin validation path. [`.github/workflows/security-scan.yml:64-94`]() [`.github/workflows/security-scan.yml:96-128`]() [`.github/workflows/security-scan.yml:130-147`]()

### Reusable gate and dependent workflows

CI, E2E, integration, UI E2E, and UI snapshot each declare a reusable `security-gate.yml` job. E2E has an additional conditional for label events: ordinary label changes short-circuit the gate job, while the `skip-security-scan` label is allowed through to the gate path. The precise polling and result-mirroring implementation of `security-gate.yml` is not shown in the supplied contents. ## Test and quality workflows

### Continuous Integration — `ci.yml`

`ci.yml` runs on pull requests and pushes to `main` and `release/v[0-9]*`. Its path filters exclude web, documentation, designs, changelog, and browser/UI E2E test paths. The workflow sets `OMNIGENT_SKIP_WEB_UI=true` and groups concurrent runs by workflow plus PR number or commit SHA, cancelling an in-progress run in the same group. [`.github/workflows/ci.yml:12-47`]()

After the security gate, the `scope` job runs the `dependency-ci-scope` action and exports the matrix and scope outputs. The `pytest` job skips draft PRs and runs only when the backend scope is true. It uses a matrix from `python_matrix`, sets up Python and `uv`, installs the test dependencies, and provisions selected system tools including `ripgrep`, `bubblewrap`, and `tmux`. Certain matrix groups install particular harness CLIs or extra system dependencies. [`.github/workflows/ci.yml:49-90`]() [`.github/workflows/ci.yml:91-147`]()

The shown pytest setup also places coverage files outside the repository worktree and configures coverage collection through `COVERAGE_CORE=sysmon`; the comments describe these choices as addressing sandbox dotfile masking and slow coverage tracing. [`.github/workflows/ci.yml:163-176`]()

Sources: `.github/workflows/ci.yml:12-47`, `.github/workflows/ci.yml:49-90`, `.github/workflows/ci.yml:91-147`, `.github/workflows/ci.yml:163-176`

### End-to-end tests — `e2e.yml`

`e2e.yml` runs the `tests/e2e/` suite against an in-process mock LLM server. It is configured for daily scheduling, pull requests, and manual dispatch; manual runs accept a `parallelism` input. The PR path filters exclude web, docs, designs, changelog, UI tests, scripts, GitHub tests, and Polly workflow files. The workflow blanks provider credentials and skips building the web UI. [`.github/workflows/e2e.yml:1-16`]() [`.github/workflows/e2e.yml:18-66`]()

The `setup` job runs dependency scope and `e2e-shard-matrix.sh`, setting `NUM_SHARDS` to eight and producing an empty matrix when tests should not run. The `e2e` job consumes that matrix with `fail-fast: false` and `max-parallel: 8`, then calls `.github/actions/e2e-run/action.yml` with shard identifiers, parallelism, and whether the run is a full nightly/manual pass. [`.github/workflows/e2e.yml:84-115`]() [`.github/workflows/e2e.yml:117-153`]()

The composite action provides common test setup for E2E and server compatibility runs. The shown steps configure a credential-scrubbed environment, set up Python and `uv`, install dependencies and system packages, and install several harness CLIs. When `server_version` is provided, it builds a tagged server in an isolated virtual environment and sets `OMNIGENT_COMPAT_SERVER_PYTHON`; the action also declares a separate `runner_version` input for runner/host compatibility runs. [`.github/actions/e2e-run/action.yml:12-53`]() [`.github/actions/e2e-run/action.yml:54-138`]() [`.github/actions/e2e-run/action.yml:140-163`]()

Sources: `.github/workflows/e2e.yml:1-16`, `.github/workflows/e2e.yml:18-66`, `.github/workflows/e2e.yml:84-153`, `.github/actions/e2e-run/action.yml:12-53`, `.github/actions/e2e-run/action.yml:54-138`, `.github/actions/e2e-run/action.yml:140-163`

### End-to-end UI tests — `e2e-ui.yml`

`e2e-ui.yml` runs Playwright tests against a freshly built web SPA, including native Claude, Codex, and Cursor render-parity tests. It supports pull requests, a daily schedule, and manual dispatch. Its environment skips the web build during dependency installation, scrubs harness credentials, and sets `TERM=xterm-256color` for PTY behavior. [`.github/workflows/e2e-ui.yml:1-13`]() [`.github/workflows/e2e-ui.yml:15-64`]()

After the security gate, the `setup` job runs `dependency-ci-scope` and `e2e-shard-matrix.sh`. The shard count is selected from the UI scope: two shards for a non-full UI scope and ten for a full scope. A separate `build-sidecar` job builds or restores the Codex parity sidecar binary, then uploads it as a short-lived artifact for test shards. The supplied excerpt shows the sidecar job’s build and artifact steps; later shard execution steps are outside the supplied excerpt. [`.github/workflows/e2e-ui.yml:66-104`]() [`.github/workflows/e2e-ui.yml:106-154`]()

Sources: `.github/workflows/e2e-ui.yml:1-13`, `.github/workflows/e2e-ui.yml:15-64`, `.github/workflows/e2e-ui.yml:66-104`, `.github/workflows/e2e-ui.yml:106-154`

### Integration tests — `integration.yml`

`integration.yml` runs journey-suite tests from `tests/integration/` using mock LLM responses and a local mock FastAPI server, without real gateway credentials. It supports a daily schedule, pull requests, and manual dispatch; PR path filters omit documentation, web, UI tests, scripts, and selected workflow files. [`.github/workflows/integration.yml:1-9`]() [`.github/workflows/integration.yml:11-50`]()

The `setup` job calls `dependency-ci-scope`, then invokes `integration-matrix.sh` with the event name, draft state, and integration scope. The `integration` job expands the generated matrix and calls `.github/actions/integration-run/action.yml` with each matrix cell’s harness, model, and worker count. The action’s implementation is not included in the supplied contents. [`.github/workflows/integration.yml:52-91`]() [`.github/workflows/integration.yml:93-121`]()

Sources: `.github/workflows/integration.yml:1-9`, `.github/workflows/integration.yml:11-50`, `.github/workflows/integration.yml:52-91`, `.github/workflows/integration.yml:93-121`

### Visual snapshots — `ui-snapshot.yml`

`ui-snapshot.yml` compares rendered UI screenshots with committed baselines. Pull-request runs first use a `detect` job to identify render-affecting changes; manual dispatch accepts an optional `ref` for baseline regeneration. The workflow uses a digest-pinned Playwright Python container so the CI comparison uses the same renderer as the documented local regeneration script. [`.github/workflows/ui-snapshot.yml:3-40`]() [`.github/workflows/ui-snapshot.yml:42-69`]() [`.github/workflows/ui-snapshot.yml:128-144`]()

The `detect` job checks out the repository, calls `dependency-ci-scope`, and obtains changed PR files through the GitHub API. It sets the UI output to true for dispatches and when the file list cannot be fetched, avoiding a false pass; otherwise it checks the changed paths against a render-input pattern. The snapshot render job is skipped when the output is false. [`.github/workflows/ui-snapshot.yml:78-127`]() [`.github/workflows/ui-snapshot.yml:128-144`]()

## Automation workflows

### Polly AI Review — `polly-review.yml`

The workflow describes a review pipeline that starts a local Omnigent server and runner, submits a PR diff to a Polly session, waits for cross-vendor review, and posts findings as a PR comment. It supports automatic PR events, `/review` issue comments, and manual dispatch with PR, expected-head, and force inputs. Its declared permissions include read access to contents and write access to pull requests. [`.github/workflows/polly-review.yml:1-19`]() [`.github/workflows/polly-review.yml:21-48`]()

For automatic `pull_request_target` events, a `gate` job calls `security-gate.yml` only for same-repository PRs. The issue-comment `trigger` job accepts commands only when the comment is a PR comment, contains `/review`, is not from a bot, and is authored by an owner/member/collaborator or a user in `REVIEW_ALLOWLIST`.
