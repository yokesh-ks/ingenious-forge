## 1. Memory Directory (`memdir`) & Concurrent Scanning

OpenClaude stores structured memories as markdown files inside a project memory directory (`memdir`). To avoid heavy synchronous reads during query turns, memory files are scanned and indexed concurrently using a worker pool and chunked frontmatter extraction.

The scanning architecture is implemented in `[src/memdir/memoryScan.ts:66-125]`, where `scanMemoryFiles` coordinates async directory traversal and worker-based metadata loading `[src/memdir/memoryScan.ts:73-125]`. Traversal is depth-bounded up to `MAX_DEPTH` (`3`), and frontmatter reads are capped by strict line and byte thresholds to protect memory overhead `[src/memdir/memoryScan.ts:24-26]`.

## 2. Conversation Arc & Phase State Machine (`conversationArc`)

Conversation arcs track high-level progress, goals, decisions, and milestones in a sidecar file (`.arc.json`) located within the memory directory. This abstracts conversation momentum away from raw transcript files.

The core implementation in `[src/utils/conversationArc.ts:45-175]` manages state across five explicit phases: `init`, `exploring`, `implementing`, `reviewing`, and `completed`. Goals maintain individual statuses (`pending`, `active`, `completed`, `abandoned`) and are validated and normalized using strict schema parsing via `normalizeArc` `[src/utils/conversationArc.ts:99-175]`. Arc writes are guarded by memory policies to respect governance requirements `[src/utils/conversationArc.ts:188-194]`.

## 3. Knowledge Graph & Compatibility Layer

OpenClaude includes a compatibility layer for the knowledge graph that delegates actual storage and vector indexing to `memdir`, maintaining legacy structural definitions (`Entity`, `Relation`, `SemanticSummary`) for backward compatibility `[src/utils/knowledgeGraph.ts:29-55]`.

When a project loads, the system attempts legacy migration from older JSON stores (`knowledge_graph.json`) or SQLite stores (`knowledge.db`) discovered via git roots or working directories `[src/utils/knowledgeGraph.ts:107-125]`.

## 4. Session Storage, Restoration & Title Generation

### Session Persistence & Transcripts
Session transcripts, log options, worktree bindings, and entry streams are serialized and stored via `[src/utils/sessionStorage.ts:1-114]`. File locking mechanisms (`withTranscriptFileLock`) prevent race conditions between concurrent asynchronous tasks writing to transcript logs `[src/utils/sessionStorage.ts:107-111]`.

### AI-Generated Session Titles
OpenClaude utilizes title generation modules to derive concise conversation titles via small fast models (`Haiku`). The initialization and bridge context handling logic interact with `[src/bridge/initReplBridge.ts:47-52]` to pull session titles and manage remote session states `[src/bridge/initReplBridge.ts:1-104]`.

## 5. Fact Extraction, Memory Policies & Stats

To keep context windows clean while retaining important context, OpenClaude extracts background knowledge facts from sessions.

- **Extraction**: The `extractFactsIntoMemdir` pipeline processes message history and persists distilled facts into the `.facts` directory managed under `memdir` `[src/utils/conversationArc.ts:15]`
- **Governance**: Memory writing requires explicit validation against governance policies (`isMemoryWriteApprovalRequired`), ensuring untrusted or restricted modes do not auto-persist sensitive files `[src/utils/conversationArc.ts:193]`.
- **Usage Statistics**: Token consumption, session runtime, and historical aggregations are tracked through runtime stats caches and diagnostic logs `[src/utils/diagLogs.ts:1]`.
