## Purpose and Scope

This document describes how Void defines and manages model capabilities across different LLM providers. It covers the static capability definitions that determine how models are configured, what features they support, and how they communicate with their respective APIs.

For information about how provider implementations use these capabilities when sending messages, see [4.2 Provider Implementations](). For details on message format conversion using these capabilities, see [4.5 Message Format Conversion](). For reasoning-specific configuration, see [4.4 Reasoning and Extended Thinking]().

## Model Capability System Architecture

Void maintains a centralized capability system that defines static properties for each model. These capabilities are immutable at runtime but can be overridden by users through the settings system.

### Core Type Structure

The `VoidStaticModelInfo` type defines all model capabilities:

```typescript
type VoidStaticModelInfo = {
  contextWindow: number;
  reservedOutputTokenSpace: number | null;
  supportsSystemMessage: false | 'system-role' | 'developer-role' | 'separated';
  specialToolFormat?: 'openai-style' | 'anthropic-style' | 'gemini-style';
  supportsFIM: boolean;
  additionalOpenAIPayload?: { [key: string]: string };
  reasoningCapabilities: false | { /* reasoning config */ };
  cost: { input: number; output: number; cache_read?: number; cache_write?: number; };
  downloadable: false | { sizeGb: number | 'not-known' };
}
```

## Context Window Management

Context windows define the maximum number of input tokens a model can process. Void reserves space for output tokens to ensure requests don't exceed limits.

### Configuration Fields

| Field | Type | Purpose |
|-------|------|---------|
| `contextWindow` | `number` | Maximum input tokens the model accepts |
| `reservedOutputTokenSpace` | `number \| null` | Tokens reserved for output (defaults to 4096 if null) |

### Examples Across Providers

| Model | Context Window | Reserved Output | Effective Input Limit |
|-------|----------------|-----------------|----------------------|
| `gpt-4.1` | 1,047,576 | 32,768 | 1,014,808 |
| `claude-3-7-sonnet-20250219` | 200,000 | 8,192 | 191,808 |
| `gemini-2.5-pro-exp-03-25` | 1,048,576 | 8,192 | 1,040,384 |
| `o3` | 1,047,576 | 32,768 | 1,014,808 |
| `deepseek-chat` | 64,000 | 8,000 | 56,000 |

### Reasoning Context Windows

Models with reasoning capabilities may reserve additional output space when reasoning is enabled:

```typescript
reasoningCapabilities: {
  supportsReasoning: true,
  reasoningReservedOutputTokenSpace: 8192,  // Overrides normal reservedOutputTokenSpace
  // ...
}
```

## System Message Support

Different providers handle system messages differently. Void abstracts these differences through the `supportsSystemMessage` field.

### System Message Modes

| Mode | Description | Providers |
|------|-------------|-----------|
| `false` | No system message support | o1-mini, some open source models |
| `'system-role'` | System message as first message with role `"system"` | OpenAI (GPT-4), Mistral, Groq, most open source |
| `'developer-role'` | System message with role `"developer"` | OpenAI (o3, o4-mini, o1 series) |
| `'separated'` | System message passed as separate parameter | Anthropic, Gemini |

### Implementation Example

```typescript
// OpenAI 'system-role'
messages = [{ role: 'system', content: systemMessage }, ...userMessages]

// OpenAI 'developer-role'
messages = [{ role: 'developer', content: systemMessage }, ...userMessages]

// Anthropic 'separated'
anthropic.messages.stream({
  system: separateSystemMessage,  // Passed separately
  messages: messages,             // No system message in array
  // ...
})

// Gemini 'separated'
genAI.models.generateContentStream({
  config: {
    systemInstruction: separateSystemMessage,  // Passed in config
  },
  contents: messages,  // No system message in array
})
```

## Tool Format Support

Void supports three native tool calling formats, with XML fallback for models without native support.

### Tool Format Types

| Format | Description | Providers | Features |
|--------|-------------|-----------|----------|
| `'openai-style'` | OpenAI function calling API | OpenAI, Groq, xAI, Mistral, local providers | Parallel tool calls, streaming support |
| `'anthropic-style'` | Anthropic tool use API | Anthropic | Rich parameter validation, tool choice control |
| `'gemini-style'` | Gemini function declarations | Gemini | Type-safe parameters, nested objects |
| `undefined` | XML tool calling fallback | Any model without native support | Uses XML tags parsed by `extractXMLToolsWrapper` |

## FIM Support for Autocomplete

Fill-In-Middle (FIM) is a specialized capability required for autocomplete features, where the model completes code given prefix and suffix context.

### FIM-Capable Models

Models with `supportsFIM: true` are designed specifically for code completion:

| Provider | FIM Models |
|----------|------------|
| Mistral | `codestral-latest`, `magistral-medium-latest` |
| Ollama/vLLM | `qwen2.5coder`, `starcoder2`, `codegemma:2b` |

### FIM Filtering in Settings

The autocomplete feature automatically filters models to only show FIM-capable options in the UI via `modelFilterOfFeatureName` in `voidSettingsService.ts`.

## Reasoning Capabilities

Models with reasoning capabilities can perform extended thinking before generating responses. Void supports multiple reasoning configuration styles.

### Reasoning Configuration Structure

```typescript
reasoningCapabilities: false | {
  readonly supportsReasoning: true;
  readonly canTurnOffReasoning: boolean;      // User can disable reasoning
  readonly canIOReasoning: boolean;           // Model outputs reasoning text
  readonly reasoningReservedOutputTokenSpace?: number;
  readonly reasoningSlider?:
    | { type: 'budget_slider'; min: number; max: number; default: number }
    | { type: 'effort_slider'; values: string[]; default: string };
  readonly openSourceThinkTags?: [string, string];  // e.g., ['']
}
```

### Reasoning Slider Types

- **Budget Slider** (Anthropic, Gemini): Controls maximum reasoning tokens via `budget_tokens`.
- **Effort Slider** (OpenAI): Controls reasoning effort level (`low`, `medium`, `high`).
- **Open Source Think Tags** (DeepSeek, QwQ): Model outputs reasoning in special tags parsed by `extractReasoningWrapper`.

## Model Overrides System

Users can customize model capabilities through the overrides system, stored in `overridesOfModel` state in the `VoidSettingsService`.

### Overridable Fields

Only specific fields can be overridden by users:
- `contextWindow`
- `reservedOutputTokenSpace`
- `supportsSystemMessage`
- `specialToolFormat`
- `supportsFIM`
- `reasoningCapabilities`
- `additionalOpenAIPayload`

## Summary

Void's model capability system provides a centralized, type-safe way to define and manage LLM model properties across providers. It bridges provider diversity with a unified capability model, enabling features like chat, autocomplete, and code editing to work seamlessly across any supported LLM.
