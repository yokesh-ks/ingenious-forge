# Branch finishing

Once a story is implemented, verified and reviewed, bring the work back in
safely: verify again, determine the base branch, offer the user exactly
the options below, carry out the chosen one following Forge's commit and PR
conventions, link the issue and project board, and clean up the workspace.

**Core rule:** the user decides how the branch lands. Never merge to
`main`, force-push or delete a branch without explicit approval.

## When not to use it

- The work is not done: verification has not passed or review findings are
  open. Run `verify-before-done` and `change-review` first.
- The user only wants to push without finishing (a plain `git push` is not
  this skill).
- Release tagging and publishing (`release-launch`, not this skill).

## Workflow

### 1. Preconditions

Both must hold before proceeding:

1. **`verify-before-done` passed on HEAD.** Look for a Verification block
   from the current turn (after the last edit). If there is none, stop:
   "Verification has not been run on HEAD. Run `verify-before-done` first."
2. **`change-review` has no open Critical or Important findings.** If
   review has not been run, or open findings remain, stop: "Review has open
   findings (or has not been run). Run `change-review` and resolve findings
   first."

If either is missing, stop and say which. Do not offer the options.

### 2. Detect the environment

Run from the directory you are in:

```bash
WORKTREE_PATH=$(pwd -P)
GIT_DIR=$(cd "$(git rev-parse --git-dir)" && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" && pwd -P)
BRANCH=$(git branch --show-current)   # empty means detached HEAD
```

Classify:

| Condition | Environment |
| --- | --- |
| `BRANCH` is non-empty, `GIT_DIR` equals `GIT_COMMON` | Normal checkout on a branch |
| `BRANCH` is non-empty, `GIT_DIR` differs from `GIT_COMMON` | Worktree on a branch |
| `BRANCH` is empty | Detached HEAD (managed externally) |

Record `WORKTREE_PATH` now; you will need it for cleanup.

### 3. Determine the base branch

```bash
git fetch origin main
BASE=$(git merge-base HEAD origin/main)
```

The base is `main` unless the branch was cut from something else. To
check: `git log --oneline origin/main..$BASE` should be empty. If not,
the branch may have been based on another feature branch; warn the user
and ask which base to use.

### 4. Present the options

**Normal checkout or worktree (branch exists):**

> The branch `<branch>` has N commit(s) over `main` (base `<short SHA>`).
>
> 1. **Merge locally** — merge into `main` in this checkout, rerun checks,
>    do not push.
> 2. **Push and open a PR** — push the branch and create a pull request
>    linked to the issue.
> 3. **Keep as is** — leave the branch and workspace; report how to resume.
>
> Which option?

**Detached HEAD:**

> HEAD is detached at `<short SHA>` with N commit(s) over `main`.
> A branch is needed before a PR or merge. Options:
>
> 1. **Push and open a PR** — create a branch from HEAD, push and open a
>    PR linked to the issue.
> 2. **Keep as is** — leave the workspace; report how to resume.
>
> Which option?

Present exactly these options in exactly this order. Wait for the user's
answer. Do not proceed until they choose. Discarding the work is not
listed; the user must ask for it explicitly.

### 5. Commit hygiene

Before any push or merge, scan every commit message on the branch for AI
attribution:

```bash
git log --format='%H %s' origin/main..HEAD
```

For each commit, check the full message:

```bash
git log --format='%B' -1 <SHA>
```

Check against the patterns in `.githooks/ai-attribution-patterns.txt`:
`Co-Authored-By:` lines naming an AI (claude, anthropic, copilot, openai,
chatgpt, codex, gemini, cursor, devin, aider, bot@), and phrases
("generated with", "generated by", "assisted by the code-assist sop").
The check is case-insensitive.

Also verify each commit title is conventional: `type(scope): subject` or
`type: subject`, where type is one of `feat`, `fix`, `docs`, `chore`,
`refactor`, `test`, `build`, `ci`, `perf`, `revert`. Git's own `Merge`,
`Revert`, `fixup!`, `squash!` and `amend!` titles pass.

**If attribution is found:** stop and report which commit(s) and line(s).
Propose a fix:

- Single offending commit at HEAD: `git commit --amend` to remove the
  line (show the clean message).
- Multiple commits or not at HEAD: propose an interactive rebase, or ask
  the user to approve a history rewrite. **Never force-push without
  explicit approval.**

Do not continue to step 6, 7 or 8 until the messages are clean.

**If a title is not conventional:** warn and propose an amend or rebase.

### 6. Option: push and open a PR

#### 6a. Create a branch (detached HEAD only)

If HEAD is detached, create a branch from it:

```bash
git switch -c <branch-name>
```

Use the naming convention from `workspace-setup`: `<type>/<slug>[-<issue>]`.

#### 6b. Push

```bash
git push -u origin <branch>
```

#### 6c. Build the PR body

Use `references/pr-template.md` as the template. Fill in:

- **Summary:** one to three sentences describing the change.
- **Linked issue:** `Closes #N` (use `Closes` for the issue this branch
  implements; use `Refs #N` for related issues that are not closed by this
  PR).
- **Changes:** bullet list of what changed, grouped by area.
- **Verification:** the evidence block from `verify-before-done` (step 1).
- **Review:** the summary from `change-review`.
- **Notes:** anything the reviewer should know, or "None."

The PR title must be in conventional-commit form: `type(scope): subject`.

**No AI attribution lines.** Do not add `Co-Authored-By` trailers for an
AI, "Generated with" lines, or any other AI attribution anywhere in the PR
body. This is Principle VII.

#### 6d. Create the PR

Write the body to a temporary file and use `--body-file`:

```bash
gh pr create --base main --title "<conventional title>" --body-file <tmp>
```

#### 6e. Add the PR to the project board

```bash
gh project item-add 34 --owner yokesh-ks \
  --url <pr-url> --format json --jq .id
```

The linked issue's status should already be **In Review** via the board's
"Pull request linked to issue" workflow. If the PR does not link the
issue (no `Closes #N`), manually set the issue to **In Review**:

```bash
item=$(gh project item-list 34 --owner yokesh-ks --format json --limit 500 \
  --jq '.items[] | select(.content.number==<n>) | .id')
gh project item-edit --project-id PVT_kwHOBAdtHM4BpdXc --id "$item" \
  --field-id PVTSSF_lAHOBAdtHM4BpdXczhn47Y8 \
  --single-select-option-id 011a42ee
```

#### 6f. Report

Print the PR URL and confirm the issue link and board status.

### 7. Option: merge locally

#### 7a. Merge

```bash
git switch main
git pull origin main
git merge --no-ff <branch>
```

If the merge fails, stop and report. Do not force it.

#### 7b. Rerun checks

Run the validation commands from `AGENTS.md` → **Development and
validation** on the merged result. If any fail, warn the user: the merge
introduced a problem. Do not push.

#### 7c. Report

Print the merge commit SHA and the check results. Do not push unless the
user asks.

### 8. Option: keep as is

Report:

> Branch `<branch>` is at `<short SHA>` with N commit(s) over `main`.
> Workspace: `<path>`.
> To resume: `cd <path>` (or switch to the worktree).

No cleanup. No push. No merge.

### 9. Clean up

**Only after a successful merge (step 7) or PR creation (step 6).** Never
after "keep as is."

#### 9a. Check for uncommitted work

```bash
git status --porcelain
```

If there are uncommitted changes, warn and do not clean up. Ask the user
what to do with them.

#### 9b. Remove the worktree (if one was created by `workspace-setup`)

Only if the current directory is a linked worktree (step 2: `GIT_DIR`
differs from `GIT_COMMON`):

```bash
cd <main checkout>
git worktree remove <WORKTREE_PATH>
```

If removal fails (uncommitted files, in use), report and leave it.

#### 9c. Delete the local branch (after merge only)

After a local merge, if the branch is fully merged into `main`:

```bash
git branch -d <branch>
```

Use `-d` (safe delete), never `-D`. If it refuses, the branch is not fully
merged; leave it and tell the user.

After a PR, do not delete the local branch: GitHub deletes it on merge.

#### 9d. Never delete unmerged branches

A branch that is not merged into `main` is never deleted without the user
saying so. Even if the PR is open, the branch stays.

### 10. Close the loop

#### 10a. Comment on the issue

If a PR was opened:

```bash
gh issue comment <n> --body "PR #<pr-number> opened: <pr-url>"
```

If merged locally:

```bash
gh issue comment <n> --body "Merged to main at <sha>."
```

#### 10b. Suggest retrospective

If this closes the last story of an epic, suggest:

> This closes the last story in epic #E. Consider running a retrospective.

## Common rationalisations

| Excuse | Reality |
| --- | --- |
| "Verification passed earlier." | Earlier is before the last edit. Check step 1 again. |
| "The review had only minor findings." | Minor or not, open findings block finishing. Resolve them. |
| "I'll just merge quickly." | Present the options and wait. The user decides. |
| "Force-push will clean up the history." | Never without explicit approval. Propose; don't act. |
| "The attribution trailer is harmless." | Principle VII. Remove it before pushing. |
| "I'll delete the branch to tidy up." | Only merged branches, only with `-d`, only after the user chose merge or PR. |
| "The worktree is in the way." | Only remove after merge or PR, never after "keep". |

## Red flags

Stop and go back if you notice any of these:

- about to merge to `main` without the user choosing option 1;
- about to push without the user choosing option 2;
- about to force-push or rewrite history without explicit approval;
- a `Co-Authored-By` or "Generated with" line in any commit or the PR body;
- about to remove a worktree or delete a branch after "keep as is";
- about to remove a worktree with uncommitted changes;
- `git branch -D` instead of `git branch -d`;
- no Verification block in the PR body;
- no `Closes #N` or `Refs #N` in the PR body.

## Outputs

- A pull request (option 2), a local merge (option 1) or a status report
  (option 3).
- The PR body follows `references/pr-template.md`.
- The issue is commented with the PR link or merge SHA.
- The PR is added to project 34.
- The worktree is removed (after merge or PR only, if one existed).
